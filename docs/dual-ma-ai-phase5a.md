# Phase 5A — autonomous READ ONLY market data and dashboard

## Scope and authorization gate

Implemented Phase 5A only. There is no autonomous PAPER portfolio, signal queue, sizing, fill or transaction capability in the worker. The persistent wallet is never imported or opened by the worker. The LaunchAgent dashboard uses `--read-only`, rejecting every POST, including virtual funding. Existing manual-dashboard wallet functionality remains available outside this read-only service; no wallet implementation/schema changes were made.

Both LaunchAgent configurations are **Disabled=true**, generated under the repository's `launchd/` directory. Neither was copied to `~/Library/LaunchAgents`, bootstrapped, enabled or started. No dependencies were installed. No commits or pushes.

Activation requires explicit user approval to install/enable the two read-only services and replace the existing Dual MA AI dashboard process occupying localhost port 8895. That process was identified as Dual MA AI without `--read-only`; it was not stopped or modified. No Turtle Mini process should ever be stopped to free this port.

## Runtime architecture

| Component | Behavior | Persistent state |
|---|---|---|
| `dual_ma_ai.monitor run` | One long-lived worker, UTC clock checked about every 60 seconds; launchd restarts after failures | Separate `data/dual_ma_ai/monitor/monitor.sqlite3` |
| IEX recent-price acquisition | One bulk nine-symbol latest-quotes GET per regular-hours refresh, no feed fallback | Latest validated bids/asks/timestamps in monitor state |
| Daily candle acquisition | Raw/split paired `1Day` GETs for a rolling 450-day interval; initial fetch and when a new completed daily candle appears | Separate `monitor/history/` immutable cache, never Phase 4.1 research history |
| Daily signal evaluator | SMA 50/200, SMA 20/50, EMA 20/50; requires 201 completed candles, current expected candle and strict validation | Informational BUY/SELL/NO CROSS events and latest snapshots |
| Dashboard service | HTTP bound only to 127.0.0.1:8895; GET status/price/signal views and wallet reads | No wallet mutations; funding requests rejected |
| Browser | Opens localhost at service startup, throttled to once an hour after crashes; page polls every 10 seconds | No page reload, no execution/funding POST generated by polling |

NYSE calendar is the existing pinned `exchange_calendars` XNYS implementation. Holiday, DST and early-close behavior is checked in regression tests against [NYSE's published hours/calendar](https://www.nyse.com/trade/hours-calendars). It models regular sessions; announcements of exceptional closures still require an updated/reviewed calendar. No dependency or calendar version was changed.

The worker stops recent-price acquisition at the calendar's regular close, including early closes. Outside regular hours it maintains a heartbeat and fetches newly finalized daily history when needed; it does not repeatedly fetch live quotes. Daily bars retain the Phase 4.1 conservative availability rule: the New York day must end plus 16 minutes, because daily aggregates can include extended-hours activity/revisions. They are not considered final at the regular session close. All timestamps are explicit UTC/offset timestamps, with NYSE/New York conversions performed by the calendar and zoneinfo, not the Mac's local timezone.

When a ticker fails daily validation, it is BLOCKED with no new signals. Other validated tickers may display informational signals; overall health is DEGRADED. Failed history retries at most every five minutes; a newly expected completed candle triggers an immediate new attempt. IEX quotes never substitute for missing daily candles or get used in MA calculations. Quotes must have positive bid/ask/size, an uncrossed spread, and a timestamp no more than 120 seconds old or in the future. Stale/invalid quotes do not claim a successful market refresh. Outside market hours retained prices are visibly aged/STALE, not fabricated fresh prices.

Overlapping historical OHLCV/split changes block that ticker for source review. No missing bar is filled, interpolated or mapped to predecessor history. Validation includes the existing strict outlier, timestamp, completed-candle, duplicate, session and raw/split price/volume checks. Historical snapshots and Phase 4.1 backtests remain untouched. The worker's separate cache retains provenance/hash and validation metadata. Unchanged payloads reuse their immutable snapshot; repeated observations do not rewrite identical daily caches or duplicate daily decision events.

## Reliability, health and security

- An OS `flock` held for the worker lifetime prevents duplicate processes/overlapping refreshes. The OS releases it after a crash. launchd runs one instance per label. The dashboard's fixed localhost port rejects a second server.
- SQLite `BEGIN IMMEDIATE`, a busy timeout, unique deterministic event IDs and immutable audit-event triggers protect state. Refresh attempts are recorded before acquisition; outcomes/snapshots are committed together. An unfinished attempt is recovered and logged on restart. Sleep/wake recomputes the current schedule and fetches current data; there is no execution path or replay of missed prices.
- Transport uses the existing closed Alpaca GET allowlist. The monitor uses only `/v2/stocks/bars` and `/v2/stocks/quotes/latest`, fixed HTTPS `data.alpaca.markets`, feed IEX, no redirects, bounded pagination, two attempts, ten-second request timeout, and existing bounded 429/5xx backoff. Normal refresh cadence is approximate: network latency and failed daily acquisition can delay a cycle, not bypass validation or spawn another worker.
- Credentials are captured with subprocess pipes from exact Keychain services `dual-ma-alpaca-api-key` and `dual-ma-alpaca-secret-key`, account the current macOS user. No shell command substitution, credential files, environment fallback, credential-bearing logs or provider error bodies are used. Secrets are sent only to the intended Alpaca data host and retained only in memory.
- Durable SQLite alerts record REFRESH, RECOVERY, BLOCKED and ERROR, plus informational BUY/SELL/NO CROSS. The worker uses bounded rotating local logs (1 MB × four files). The dashboard shows recent alert explanations. No email, Slack or external notification is sent. LaunchAgent stdout/stderr files are local; they may require maintenance if repeated startup failures occur.
- RUNNING means a fresh worker heartbeat and healthy latest acquisition. DEGRADED means partial validation/quote failure. STALE means the expected candle or active-session quote has aged beyond its threshold. ERROR means transport/Keychain/state failure. STOPPED means services absent, explicitly stopped, or heartbeat older than three minutes. A daily signal is hidden when its candle no longer matches the expected completed session.
- Background services cannot run while the Mac is asleep/logged out, nor unlock Keychain automatically. On wake/login launchd/worker recovery resumes current observations. Browser launch is convenience, not forced kiosk mode: closing the browser does not stop the worker/server, and macOS may require approval to open the browser.

The disabled user LaunchAgents use RunAtLoad, KeepAlive, restart throttling, absolute Python/repository paths, and restrictive umask. This follows [Apple's user LaunchAgent/KeepAlive architecture](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html). No sudo, Docker or privileged daemon is involved.

## Prerequisites and current blockers

1. Existing `.venv/bin/python`, installed/pinned exchange-calendar dependencies, and a stable repository path. Generate LaunchAgent plist files on the target machine so paths point to that checkout; no new packages are required now.
2. A logged-in macOS user with unlocked Keychain, the two exact items, and permissions allowing `/usr/bin/security` to read them without an unattended prompt. The read-only live dry-run verifies retrieval in the current session; background/login ACL behavior remains to be confirmed after approved installation.
3. Internet access to the intended Alpaca host, IEX entitlements, and macOS permission for these user background services/default-browser launch if prompted.
4. Port 8895 must be released by the verified existing Dual MA AI dashboard after approval, then replaced by the read-only service. No existing process was stopped during this phase.
5. SPCX/AAOI outliers remain unresolved and block those tickers. Older COHR discontinuity, IEX history gaps, provider revisions, retrospective identity/universe assumptions and lack of total-return data remain. No missing ten-year/full-universe performance is invented.

Phase 4.2 was independently rerun against the frozen MU report: all nine runs/6,792 daily rows passed. Zero one-year fills are explained by crossover/whole-share allocation behavior; closed realized losses and open unrealized gains reconcile. No required financial-engine correction was outstanding. No sizing policy is introduced in Phase 5A.

```sh
cd "$HOME/dual-ma-tortuga"
.venv/bin/python -m dual_ma_ai.launch_agents
/usr/bin/plutil -lint launchd/local.dual-ma-ai.market-data.plist launchd/local.dual-ma-ai.dashboard.plist

```

Generation creates only disabled, machine-specific plist files under `launchd/`; these generated files are ignored by Git because they contain absolute paths for the current checkout. Generate them on the target machine before linting or installation. `dry-run` retrieves Keychain credentials and performs read-only IEX requests, with every state/cache write confined to a temporary directory removed afterward. It explicitly probes quote access even outside trading hours, where old quotes are rejected, not displayed as fresh. It never creates the runtime monitor DB or opens/mutates any wallet. A dry-run snapshot's RUNNING/DEGRADED fields describe its temporary simulation, not active background services.

The verified production acceptance is recorded in [the final Phase 5A acceptance report](dual-ma-ai-phase5a-final-live-acceptance.md) with privacy-filtered measurements in its evidence JSON.

## Installation after explicit approval only

These are deployment instructions, **not actions taken in this phase**. The approval must cover installing/enabling both user services and replacing the existing verified Dual MA AI dashboard. First recheck the port/PID identity and wallet integrity. Stop only that verified dashboard process with SIGTERM; do not kill an unknown service or Turtle Mini.

```sh
cd "$HOME/dual-ma-tortuga"
mkdir -p "$HOME/Library/LaunchAgents" data/dual_ma_ai/monitor
.venv/bin/python -m dual_ma_ai.launch_agents
/usr/libexec/PlistBuddy -c 'Print' launchd/local.dual-ma-ai.market-data.plist
/usr/libexec/PlistBuddy -c 'Print' launchd/local.dual-ma-ai.dashboard.plist
cp launchd/local.dual-ma-ai.market-data.plist "$HOME/Library/LaunchAgents/"
cp launchd/local.dual-ma-ai.dashboard.plist "$HOME/Library/LaunchAgents/"
/usr/libexec/PlistBuddy -c 'Set :Disabled false' "$HOME/Library/LaunchAgents/local.dual-ma-ai.market-data.plist"
/usr/libexec/PlistBuddy -c 'Set :Disabled false' "$HOME/Library/LaunchAgents/local.dual-ma-ai.dashboard.plist"
launchctl enable "gui/$(id -u)/local.dual-ma-ai.market-data"
launchctl enable "gui/$(id -u)/local.dual-ma-ai.dashboard"
launchctl bootstrap "gui/$(id -u)" "$HOME/Library/LaunchAgents/local.dual-ma-ai.market-data.plist"
launchctl bootstrap "gui/$(id -u)" "$HOME/Library/LaunchAgents/local.dual-ma-ai.dashboard.plist"
```

Repository templates remain disabled. Installed jobs start at user login and restart if they exit. The dashboard opens at **http://127.0.0.1:8895** and polls its read-only status/prices/signals every ten seconds. No manual Terminal command or dashboard refresh is needed during normal operation. Verify both jobs using `launchctl print gui/$(id -u)/local.dual-ma-ai.market-data` and the dashboard label; check READ ONLY UI, worker heartbeat, logs, blocked tickers and the unchanged wallet and audit-history digests. A background service must not be declared successfully deployed before those post-install checks pass.

## Rollback / stop

```sh
launchctl disable "gui/$(id -u)/local.dual-ma-ai.market-data"
launchctl disable "gui/$(id -u)/local.dual-ma-ai.dashboard"
launchctl bootout "gui/$(id -u)/local.dual-ma-ai.market-data"
launchctl bootout "gui/$(id -u)/local.dual-ma-ai.dashboard"
/usr/libexec/PlistBuddy -c 'Set :Disabled true' "$HOME/Library/LaunchAgents/local.dual-ma-ai.market-data.plist"
/usr/libexec/PlistBuddy -c 'Set :Disabled true' "$HOME/Library/LaunchAgents/local.dual-ma-ai.dashboard.plist"
```

If a job is already stopped, bootout may report it absent. Retain monitor logs/audit DB for review; do not delete or reset any wallet/history. Returning to the previous manual dashboard is optional and requires choosing its mode explicitly; the read-only dashboard can be manually started with `.venv/bin/python -m dual_ma_ai.dashboard --read-only` after the port is free.
